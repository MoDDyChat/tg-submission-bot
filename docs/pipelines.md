# Пайплайны tg-submission-bot

## Пайплайн зрителя

1. `/start` → бот отвечает правилами предложки
2. Зритель отправляет текст или поддерживаемый контент (фото/видео/анимация/документ) → описание сохраняется в `caption` в исходном виде с сохранённым HTML-форматированием (жирный, курсив, ссылки); `tags` остаётся пустым — теги управляются только через визард модератора
3. Бот подтверждает: «Пост #N принят» + кнопка «Отменить предложение»
4. **Пост публикуется в тему форум-группы модератора**: каждый зритель имеет свою тему в `MODERATOR_GROUP_ID`; для медиапоста — медиа + статусная карточка с кнопкой «Редактировать»; для text-only — только текстовая карточка
   - Если отправка в тему не удалась — пользователь получает уведомление об ошибке
5. Поддержка альбомов (media groups): буферизация 2 сек с `asyncio.Lock` per group_id для корректного сбора всех элементов. Если в альбоме несколько файлов с подписями — используется только подпись первого, остальные игнорируются с предупреждением пользователю
6. Кнопка «Отменить» — отменяет пост со статусом pending; пост в канале модератора переводится в финальный статус и теряет кнопку редактирования
7. При публикации в канале — зритель получает уведомление

**Ограничения:** пустое текстовое сообщение не принимается; итоговый plain-text лимит — до 1024 символов для медиапоста и до 4096 для text-only; неподдерживаемый тип медиа (стикер, голосовое и т.п.) — бот отвечает «Этот тип медиа не поддерживается». Забанённый пользователь (`is_banned`) — получает сообщение о блокировке, предложения не принимаются.

## Группа модератора (форум-темы)

Приватная Telegram-группа с поддержкой форума (`MODERATOR_GROUP_ID`), в которой модераторы видят все поступающие предложения. Каждый зритель имеет свою отдельную тему (создаётся при первой отправке, записывается в `user_topics`).

**Как работает:**
- При создании submission → `topics.post_submission_card()` отправляет медиа (если есть) + статусную карточку с кнопкой «Редактировать» в тему зрителя
- При изменении caption/тегов/статуса → `topics.update_submission_card()` обновляет текстовую карточку в теме (через `edit_message_text`)
- При публикации/отклонении/отмене → `topics.finalize_submission_card()` финализирует карточку (убирает кнопку «Редактировать»), пост остается в теме для истории
- При старте бота `ensure_general_topic_nav()` создаёт или переиспользует закреплённое навигационное сообщение с легендой статусов в General-топике форума

**Статус в названии темы:** `[LABEL] - Имя` отражает агрегатный статус пользователя (`compute_topic_status_key`, приоритет: editing > pending > scheduled, затем терминальные; published важнее прочих терминальных). Переход статуса не вызывает Telegram напрямую: `request_topic_title_sync()` атомарно увеличивает `user_topics.title_sync_version` в той же транзакции, что и доменное изменение. При откате обе записи откатываются вместе, поэтому Telegram не может опередить БД.

**Outbox заголовков:** `topic_title_sync_job` запускается каждые 10 с, сначала закрывает накопившиеся no-op revisions без Telegram-вызовов, затем применяет не более одного реального `editForumTopic`. После успеха он записывает отправленный статус в `current_status_key` и продвигает `title_applied_version` до захваченной revision. Если во время запроса пришло новое изменение, `title_sync_version` остаётся впереди и задача не теряется; при ошибке применённая версия не меняется, поэтому попытка повторится. Воркер разбит на три фазы, каждая БД-фаза — **отдельная короткая транзакция**: `_claim_next_title_revision()` захватывает ревизию и коммитит, `editForumTopic` вызывается вне транзакции, `mark_topic_title_sync_applied()` пишет результат в новой. Держать транзакцию открытой через сетевой вызов нельзя: зависший запрос удерживал бы row lock на `user_topics` и блокировал всех писателей за собой (см. `docs/architecture.md`). Встроенные retry также выдерживают минимум 10 с между запросами; `TOPIC_NOT_MODIFIED` считается успехом. Ручное переименование темы модератором ставит forced revision через `title_force_sync_version`, а служебное сообщение от собственного изменения бота повторно задачу не создаёт. Миграция один раз ставит forced revision всем существующим темам, чтобы безопасно вылечить остаточный дрейф старого direct-write механизма с тем же лимитом 10 с.

**Self-heal названий:** `topic_titles_reconcile_job` каждые 10 мин только сравнивает вычисленный статус с `current_status_key` и ставит обнаруженный дрейф в outbox; Telegram API из reconcile не вызывается. Уже ожидающая revision повторно не увеличивается. Ночного слепого переутверждения всех активных тем нет.

**Формат карточки в теме форума:**
```
{status_emoji} Пост #{sub_id}
Статус: {status_label}
[Публикация: {time}]    ← только для scheduled
[Теги: #Tag1 | #Tag2]   ← если есть
[Описание: {caption}]
```

**Self-heal карточек:** `submissions.card_rendered_hash` хранит sha256 от последнего payload (текст + клавиатура), который Telegram подтвердил. Хэш пишется только после успешной отправки/правки — провал оставляет старое значение. `topic_cards_reconcile_job` каждые 10 мин заново рендерит карточки-кандидаты, сравнивает хэши и правит только расхождения, не более 5 за проход с паузой 2 с между ними. В выборку (`list_cards_for_reconcile`) попадают все активные посты с карточкой и терминальные не старше 48 ч — финализированный пост больше не меняется, поэтому сканировать архив бессмысленно. `NULL`-хэш (строки до миграции `o3p4q5r6s7t8`) считается дрейфом и чинится один раз. Если карточки в теме уже нет — `topic_card_message_id` очищается, дальше её восстанавливает Recover. Фазы те же, что у outbox заголовков: `_collect_card_repairs()` считает дрейф в read-only транзакции и коммитит, `editMessageText` идёт вне транзакции, `mark_card_rendered_if_unchanged()` / `clear_topic_card_ids()` пишутся в отдельных коротких транзакциях — ни retry-пауза, ни задержка между починками не удерживают row lock на `submissions`. Запись хэша из reconcile — **условная** (CAS по `card_rendered_hash`): план починки строится по хэшу, прочитанному до медленного Telegram-вызова, и за это время карточку мог перерисовать держатель лока. Если хэш ушёл, запись не применяется и пост не считается починенным (счётчик `repaired` растёт только по фактически применённой записи). `mark_card_rendered()` (и её условный вариант) пиннят `updated_at` к текущему значению, чтобы `onupdate` не сдвигал временное окно выборки reconcile.

**Устойчивость карточек:** `update_submission_card` и `finalize_submission_card` редактируют карточку через `_edit_card_with_retry` — до 3 попыток с retry на `TelegramRetryAfter` и `TelegramNetworkError` (ожидание не более 30 с; более долгий `retry_after` пробрасывается сразу). `message is not modified` считается успехом и не логируется как ошибка. Retry необходим потому, что квота `EditMessageText` в модгруппе делится с доской очереди (`topics_queue`), и на всплесках карточка иначе навсегда застывала бы в старом состоянии.

**Доска очереди:** `_render_queue_inner` / `_render_schedule_inner` коммитят read-only фазу (строки очереди, чанки, текст расписания и их чексуммы) до первого Telegram-вызова. `message is not modified` считается успехом и **записывает чексумму** в `system_messages` — иначе каждый следующий проход снова упирался бы в тот же no-op edit. Лишний чанк удаляется из `system_messages` только если Telegram подтвердил удаление или сообщения уже нет (`message to delete not found`); при любой другой ошибке строка остаётся, и удаление повторится на следующем проходе.

**Устойчивость:** ошибки при отправке в форум пробрасываются вызывающему коду (`post_submission_card` — критическая операция). В handler'е зрителя — ловятся и отображается сообщение об ошибке. Посты без `topic_card_message_id` — update/delete — no-op.

## Пайплайн модератора

1. `/start` у модератора в ЛС открывает **панель модератора** с кнопкой `Управление`
2. В `Управлении` доступны глобальные инструменты (разделы **Пресеты** и **Забаненные** блокируются edit-lock на 10 минут — только один модератор редактирует одновременно):
   - **Пресеты тегов** → список разделов → добавление / переименование / удаление раздела → внутри раздела просмотр элементов, добавление, изменение `label`, изменение `tag`, удаление. Только администратор видит кнопку **Recover постов**
   - **Забаненные пользователи** → список заблокированных пользователей с разблокировкой по кнопке
   - **Recover постов** *(только администраторам)* → запуск восстановления потерянных карточек в теме форума
3. Модератор видит новые посты в **форум-группе модератора** — каждый зритель имеет свою тему, в ней публикуются медиа + карточка с кнопкой «Редактировать»
4. Нажатие «Редактировать» → deep link `t.me/{bot}?start=review_{sub_id}` → открывается DM с ботом; берётся edit lock (статус поста остаётся `pending`), карточка в теме обновляется → показывается превью с медиа + кнопки действий
5. Кнопки действий (контекстные по статусу):
   - **Редактировать описание** → FSM: ввод нового текста (валидация длины с учётом тегов: до 1024 символов для медиапоста и до 4096 для text-only; считается по plain text) → сохранение в HTML (форматирование сохраняется) → повторный показ + обновление в теме. Теги НЕ затрагиваются
   - **Редактировать теги** → динамический wizard: страницы всех разделов из БД по порядку + custom page (см. docs/tags-system.md)
   - **🖼 Редактировать медиа** → FSM (`editing_media`): открывает менеджер вложений со списком текущих медиа (номер, тип, кнопка ❌ удалить), кнопкой «➕ Добавить медиа» и «← Готово»
      - Удаление: кнопка ❌ рядом с элементом → `delete_media()` + перерисовка менеджера. Нельзя удалить последнее вложение
      - Добавление: переход в `adding_media` → модератор отправляет медиа (одиночное или альбом). Для альбома — буферизация через `media_append.buffer_append_media_group()` (2 сек ожидания, сбор всех частей), валидация состава (`validate_media_group_composition`) и асинхронный lock per `sub_id`. Для одиночного — синхронное добавление через `append_media_to_submission()`
      - При изменении состава (по сравнению с сигнатурой `media_sig_open` при открытии) — `repost_submission_card()` пересоздаёт медиа в теме форума, затем `update_submission_card()` обновляет карточку; в тему отправляется `TOPIC_NOTIFY_MEDIA_CHANGED`
      - **Посты старше 48 ч:** Telegram запрещает `deleteMessage` для сообщений старше 48 часов. Старый блок медиа удалить нельзя — он остаётся в теме как осиротевший. Редактирование собственных сообщений лимита по возрасту не имеет, поэтому старая карточка переписывается в `TOPIC_CARD_OUTDATED` (помечается устаревшей) и теряет кнопку «Редактировать» (`_mark_card_outdated`), а свежий блок постится ниже. Ошибка `message can't be deleted` обрабатывается как доброкачественная (INFO, без трейсбека), `delete_submission_card` не считает операцию провалом
      - Состав валидируется по правилам Telegram: фото+видео совместимы; документы — только с документами; GIF (animation) — только одиночно
   - **Опубликовать сейчас** *(только для `pending`)* → FSM: диалог подтверждения с превью → немедленно создаёт Publication + вызывает `publish_post()` напрямую; при ошибке — сообщение модератору, состояние откатывается к `viewing_post`
   - **Запланировать публикацию / Изменить время** → FSM: inline-календарь → час → минуты → подтверждение; время конвертируется в UTC перед сохранением; при повторном планировании обновляется существующая publication
   - **Снять с расписания** *(только для scheduled)* → отменяет APScheduler job, удаляет publication, возвращает статус в pending; очищает FSM data (`schedule_message_id`, `prompt_message_id`)
   - **Связаться с автором** → FSM: ввод сообщения → пересылка зрителю
   - **Отклонить** → FSM: ввод причины отклонения → статус rejected + уведомление зрителю + финализация карточки в теме форума
   - **Отклонить тихо** → сразу переводит пост в `rejected`, финализирует карточку в теме форума и не отправляет зрителю уведомление
   - **Заблокировать автора** → FSM: ввод причины → `is_banned=True` + `ban_reason` в БД; разблокировка выполняется через `Управление` → `Забаненные пользователи`
   - **Закрыть** → удаляет все DM-сообщения превью (медиа, кнопки, промпт) и очищает FSM
6. `/cancel` — модераторский handler очищает FSM + удаляет все превью-сообщения из DM, включая management message и любые промпты CRUD

После редактирования описания: промпт и ответ модератора удаляются, медиа перерисовывается с актуальным текстом. После визарда тегов: сообщение визарда удаляется, превью перерисовывается. После менеджера медиа: если состав изменился — карточка в теме пересоздаётся, иначе просто возвращается превью.

`/cancel` в состоянии `editing_media` / `adding_media` (категория `"sub"`): отменяет ожидающие добавления (вызов `cancel_append_for_sub`), продлевает лок, удаляет sub-state сообщения, возвращает в `viewing_post` без освобождения лока. Медиа, уже записанные в БД, остаются; незавершённый альбом отменяется.

### FSM-состояния модератора (ModeratorReview)

```
viewing_post → editing_caption
             → editing_tags_presets → editing_tags_custom
             → editing_media → adding_media
             → entering_reject_reason
             → entering_ban_reason
             → picking_date → picking_hour → picking_minute → confirm_schedule
             → confirm_publish_now
```

**FSM data, хранимый в state при просмотре поста:**
- `sub_id` — ID текущего поста
- `media_message_ids` — список ID медиа-сообщений (для удаления при навигации/ре-рендере)
- `actions_message_id` — ID сообщения с кнопками «Выберите действие»
- `prompt_message_id` — ID промпта при редактировании/отклонении/добавлении медиа
- `wizard_message_id` — ID сообщения визарда тегов
- `media_manager_message_id` — ID сообщения менеджера медиа (для удаления при закрытии)
- `media_added_message_ids` — список ID сообщений-подтверждений добавления медиа
- `media_sig_open` — отсортированный список `media.id` при открытии менеджера (для детекта изменений)
- `management_message_id` — ID домашнего экрана модератора / меню управления

**Дополнительные FSM data при визарде тегов:**
- `wizard_caption` — текущее описание (для превью)
- `wizard_sections` — словарь `section_key -> list[tag]` для выбранных пресетов по каждому разделу
- `wizard_custom` — список кастомных тегов
- `wizard_page_index` — текущая страница динамического wizard
- `wizard_message_id` — ID сообщения визарда (для in-place редактирования)

**Дополнительные FSM data в management UI:**
- `management_message_id` — одно редактируемое сообщение для домашнего экрана / меню / CRUD
- `management_preset_type` — текущий ключ раздела пресетов (`category`, `setting`, `character`, `section_N`, ...)
- `management_preset_id` — текущий выбранный элемент пресета

**Edge-case поведение:** если раздел или пресет исчезает, пока модератор открыт в wizard, уже выбранные значения не теряются и автоматически переносятся в `wizard_custom`.

### Календарь и выбор времени

- Inline-календарь с навигацией по месяцам (◀ ▶)
- Прошедшие даты заблокированы (отображаются как «·»)
- Часы: сетка 6×4 (00–23); если дата сегодня — прошедшие часы заблокированы
- Минуты: шаг 5 мин (00–55, 3 ряда по 4); если сегодня и текущий час — прошедшие минуты заблокированы (строго меньше текущей, текущая минута доступна)
- Кнопка **← Назад** на экране часов (→ к календарю), на экране минут (→ к часам) и на экране подтверждения (→ к выбору минут, сохраняя выбранную дату и час)
- Финальное подтверждение: «Подтвердить / Изменить время / Отмена»; при подтверждении валидируется что дата ещё в будущем

## Связь модератор ↔ зритель

1. Модератор нажимает «Связаться с автором» при просмотре поста
2. Вводит текст → бот пересылает зрителю с пометкой «Сообщение от модератора по поводу поста #N»
3. Зритель отвечает **reply** на сообщение бота текстом → фильтр `IsModeratorReply` перехватывает реплай → бот извлекает `sub_id` из текста (regex `msg.VIEWER_REPLY_PATTERN` из `core/messages.py`) и пересылает сообщение всем модераторам из `config.moderator_ids`
4. Если зритель отвечает reply медиафайлом — бот отклоняет с подсказкой (медиа в ответах не поддерживаются)
5. При изменении состава медиа в теме форума отправляется `TOPIC_NOTIFY_MEDIA_CHANGED` (🖼 Состав медиа изменён модератором)
6. Все текстовые сообщения сохраняются в таблице `messages`
